# Automatic response queue

## Standing authorization from Alexis

Alexis authorizes this skill, without a new approval step, to analyze a human CHANGES_REQUESTED review on an open EnerZam/JouleMV PR authored by alchambron, implement the feedback and necessary CI repairs for that PR, commit, push normally, reply to the addressed review comments, and re-request the original human reviewer. This authorization covers at most two fixer rounds per PR per feedback batch. It overrides only respond-all's combined-plan approval within this exact scope. Repository rules and explicit current user limits remain binding. Never merge, approve, force-push, resolve threads, modify another author's PR, or contact anyone beyond those replies and reviewer re-requests. A mixed-author stack is excluded in its entirety.

Read [automation.md](references/automation.md) for trigger, command, recovery and digest contracts. Installing this skill creates no schedules. Events are wake-up hints; current GitHub evidence controls every action.

## Coordinate the queue

1. Read [respond-all](../respond-all/SKILL.md) and [respond](../respond/SKILL.md). Check companion versions with the queue helper. Keep their logic unchanged; reuse their collector, history, ledger, analyzer/fixer references, publisher and renderer. For separately installed skills pass `--respond-all PATH --respond PATH` to every queue command.
2. Verify this Mac is online, available and idle through current host/coordinator evidence. Missing or ambiguous evidence means skip this run, record why and export the digest. Never infer readiness from elapsed time or an event. `--host-ready` attests this check; it is not a probe. Read saved active reservations and reconcile existing workers before new dispatch.
3. Run `queue.py plan --output SELECTION.json`. Initialize a respond-all run with `ledger.py init`, then `ledger.py queue RUN_DIR --discovery SELECTION.json`. Persist authorization evidence from this section and set ledger limits to two analyzers, one fixer and one heavy operation. Keep deferred items for later wake-ups. Repeated feedback batches resume their saved run rather than starting a new one, even when fresh discovery excludes them after an author push.
4. Claim `analysis` immediately before dispatch. At most two analyzers machine-wide, with no builds, tests, installs or runtime starts. Use respond's analyzer reference and exact-head artifacts. Save the analysis/coverage inventory and render the concrete plan to disk; standing authorization allows execution without presenting an approval question. Finish the analyzer reservation only after the worker exits.
5. Claim `fix` before dispatching a fixer; one active fixer machine-wide across queue runs/threads. Use the isolated one-writer checkout and respond fixer reference. A claim consumes one of two durable rounds, including interrupted attempts. Analyzers and fixers must all use this same Mac state directory; unrelated response fixers must acquire this queue's fixer reservation too. Every build, test, install or runtime start uses respond's `heavy_lock.py --slots 1 -- COMMAND` with the shared default `REVIEW_STATE_ROOT`; do not redirect its lock root or increase slots.
6. Before **each push**, run `guard --token TOKEN --head EXPECTED_REMOTE_SHA --snapshot PLAN_OR_SNAPSHOT` with the analysis plan holding the original `humanFeedbackSnapshot`; verify local changes belong only to the eligible PR and push normally. Before **each reply and re-request**, run guard again. Preserve respond's original `humanFeedbackSnapshot` and use `publish.py` with one external action per invocation so each action gets its own fresh eligibility guard. The guard also requires every changes-requested trigger in the frozen batch to remain its reviewer's latest decisive review and live human feedback to match that snapshot. Restrict plans to replies on the triggering human review's comments (review-body answers may use a PR conversation reply) and re-requests of its human reviewers; context/bot findings get `publish:false`. Never use an event payload as authorization or current evidence. A failed guard stops writes and becomes a handoff.
7. Immediately link every pushed PR. Wait for settled exact-head CI through the supported watcher, releasing the fixer only after its worker/runtime exits. Finish the fixer as `waiting_ci` with the pushed head (also listed in `commits`) and pending CI on that head; a fixer that pushed nothing finishes as `no_push`. While any batch of the PR waits for CI, no fixer may start on that PR. On a settled notification, record `observe-ci` for the exact pushed head before another claim; another fix round needs settled passed/failed CI on that head and a claim at that head. With passing CI and all publication verified, settle the respond ledger on the pushed head then run `complete`, the only route to `completed`; missing CI requires reconciliation or `handoff`. Completed and handed-off batches stay terminal. Missing checks, infrastructure failures, offline host, uncertain write, new feedback or stale analysis require reconciliation or a clear handoff, never an inferred pass. Batch all actionable settled failures into the next round. At two rounds, hand off to Alexis with remaining defects and exact reason. A new feedback batch requires fresh analysis and a distinct identity; it does not erase an unfinished prior batch.
8. Finish each reservation using a compact outcome JSON. Record actual pushed commit SHAs, verified reply URLs, reviewer request readbacks, exact-head CI and remaining drafts separately. Call respond-all `history.py record RUN_DIR` after verified publication/final handback; blocked or handed-off work must remain blocked in its ledger, not falsely marked handled. Export `queue.py digest` on every handback, including empty/skipped runs. Stop watchers at final handback. The digest is the handoff to Alexis; send no separate messages.

Reservations never expire. After interruption, retain them until the named worker, checkout writer and runtimes are verified stopped; reconcile push and publication journals before finishing. A lost token is recovered from the reservation's `token` in `state.json` or the digest (matching number, phase, thread and run directory), and is finished only after that cleanup is verified. Never reset rounds, remove claims or use another state directory to bypass a reservation.
