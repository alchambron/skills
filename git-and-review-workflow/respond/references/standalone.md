# Standalone response

Use this path for a direct `/respond` or `$respond`. Follow the caller's authorization when another skill dispatches the work.

## Verify the target and write eligibility

- Resolve a URL to its repository and PR number. Qualify a number with the intended repository. Read the live PR state, author login, head repository, branch and full SHA. For an execution run, use the existing credential for GitHub writes to read its current login. The bundled publisher uses `gh api user --jq .login` for identity. Compare that login with the live PR author case-insensitively. Require an open PR, a matching author, a verifiable head repository and branch, and applicable repository permission before writes. Repository access and fork ownership alone do not establish PR authorship.
- Read the target repository's applicable instructions at the pinned revision. Use live GitHub identity for rules that depend on who the current user is. A username that only describes an identity in local documentation, a filesystem path, or Git commit configuration cannot establish account ownership. An explicit repository rule allowing writes only for a named account or author still applies. If the verified identity conflicts with that rule, cite the exact instruction, state the verified login and PR author, and continue with permitted steps. Report that conflict separately from authentication, GitHub permission or branch-protection failures. An approval to execute the plan cannot grant GitHub access or waive a repository restriction.
- Use the supported PR read tools for metadata and GitHub API reads for any missing fields or feedback pages. Try existing authentication before reporting a blocker. If a read fails, identify the failed read and what remains unverified. A write's success requires a supported readback. Preserve drafts and verified results for any step that remains blocked.

## Analyze, execute and hand off

1. **Analyze.** Pin the exact head and follow the [analyzer phase](analyzer.md). Record the original `analyzedAt` and `humanFeedbackSnapshot`, in-scope rows, authorization source and action limits. List the proposed fixes and checks, push destination, reply targets, reviewer requests and CI follow-through. Initialize the shared ledger with `python3 ~/.codex/skills/respond-all/scripts/ledger.py init --root ~/.codex/review-runs/respond` so standalone runs stay outside batch discovery. Use one `create` operation for the target PR and pass the exact run directory to progress commands. See the [ledger reference](../../respond-all/references/run-ledger.md). A plan-only run ends with the report. A later go-ahead starts execution of the saved plan within its action limits. In an authorized run, share the plan as progress and proceed.
2. **Fix and verify.** Follow the [fixer phase](fixer.md) in a one-writer checkout of the pinned head. Run focused checks and use the target repository's validation policy. Commit only authorized changes. When no fix is needed, proceed with any authorized replies and reviewer requests.
3. **Recheck and push.** Immediately before a normal push, verify live ownership and the same head repository, branch and SHA. Compare the actual remote branch SHA with the pinned head. Use `publish.py --dry-run` on the original analysis or a preflight plan with the original `analyzedAt`, original snapshot and pre-push SHA to check human feedback freshness without publishing. Require a successful preflight. If the head or feedback changed, re-analyze and revise affected drafts before continuing. Carry an approval of a specific plan forward only for its concrete scope. A materially expanded plan needs its own authority. Push only the verified branch and read back the resulting SHA from GitHub.
4. **Publish and verify.** Recheck eligibility on the final head before publishing. Use the original `analyzedAt` and `humanFeedbackSnapshot` with the expected final SHA. Publish only authorized replies and requests for original human reviewers whose feedback was addressed, preserving existing requests. Use the shared publisher's readbacks and journal for reply URLs and request outcomes. If checking via `gh pr view`, reviewer logins are in `reviewRequests[].login`. For an uncertain write, reconcile by replaying the same plan through the publisher before attempting another write. Keep excluded or blocked replies as drafts. Publish fix claims only for completed work.
5. **Hand off CI.** The parent links a pushed PR immediately, then records or watches exact-head CI after publication. Reuse an existing watch when resuming. With no push, report the exact-head CI readback. Report the pushed SHA, focused checks, verified replies and reviewer requests, CI status and any concrete blockers or drafts. Follow the shared watch and follow-up rules. A local patch or push is an intermediate result while authorized steps remain.
